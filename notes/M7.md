## Plan from chat

**Feature:** Note search — a free-text search bar on the home page that filters the notes list in real time against both title and body.

---

**Design from chat:**

### Data model changes
None. Notes stay as `{"title": "...", "body": "...", "tags": [...]}` in the in-memory list. Search is a read-only filter — no new keys, no new storage.

### Route changes
- `GET /` already accepts `?tag=` — extend it to also accept `?q=` (the search query).
- If `q` is present and non-empty, filter `app.notes` to notes where `q.lower()` appears in `note["title"].lower()` or `note["body"].lower()`.
- `q` and `tag` can coexist: apply tag filter first, then search filter (or vice versa — order doesn't matter for an AND relationship).
- Pass `q` back to the template so the search box stays populated.

### UI changes
- Add a `<form method="GET">` search bar above the filter chips in `home.html`.
- Single `<input type="search" name="q">` with a placeholder ("Search notes…"), pre-filled with `{{ q or '' }}`.
- A submit button ("Search") — no JavaScript required, plain form GET.
- When results are empty, show "No notes match your search." instead of "No notes yet."

### Edge cases to handle
1. **Empty query** — `?q=` with no value should behave the same as no `q` param (show all notes). Strip whitespace before checking.
2. **Query + tag filter together** — both active at once should AND the results, not OR.
3. **Case sensitivity** — search should be case-insensitive (`lower()` on both sides).
4. **Single-character query** — no minimum length; keep it simple, filter on whatever is typed.
5. **HTML special characters in query** — Jinja2 auto-escapes template output, so `{{ q }}` in the input value is safe. No extra handling needed.

### What's out of scope
- No live/instant search (no JavaScript fetch) — plain form submit keeps it simple.
- No search highlighting in results.
- No search across tags (tags have their own filter bar already).
- No pagination.
